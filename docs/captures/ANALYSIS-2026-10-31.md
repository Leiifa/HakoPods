# Capture analysis — 2026-10-31

Two captures from the paired AirPods Pro (`23's AirPods Pro`, product ID `0x200E`) on
Windows 11 build 26200, MediaTek RZ616, adapter `0xACF23CB96170`.

| File | Window | Packets | Distinct addresses |
|---|---|---|---|
| `2026-10-31-lid-open.md` | 60 s | 59 | 1 |
| `2026-10-31-lid-cycles.md` | 150 s | 68 | 4 |

All packets were Apple manufacturer data (`0x004C`), type `0x07`, 27-byte payloads.
Method: passive BLE advertisement scanning only — no pairing, no connection, no admin.

## 1. Byte map — confirmed against hardware

Payload after the company ID, offsets as in `docs/RESEARCH.md` §5.

| Offset | Meaning | Observed | Verdict |
|---|---|---|---|
| 0 | type | `0x07` | confirmed |
| 1 | length | `0x19` (25) | confirmed |
| 2 | prefix | `0x01` | confirmed |
| 3–4 | product ID | `0E 20` → `0x200E` | **confirmed little-endian** (AirPods Pro) |
| 5 | status | `0x01`, `0x50`, `0x54`, `0x55` | confirmed bit layout (below) |
| 6 | battery | `0x44` → L 40 %, R 40 % | confirmed |
| 7 | charging + case | `0x8F` → case 80 %, charging bits set | confirmed |
| 8 | lid | `0x01` open / `0x09` closed (bit 3) | **confirmed** |
| 9 | colour | `0x00` | confirmed |
| 10 | connection state | `0x00`, `0x04`, `0x05` | confirmed (idle / music) |
| 11–26 | encrypted tail | constant for a given state | confirmed stable, not per-packet |

### Status byte, observed values

| Value | Bits set | Interpretation (matches RESEARCH §5.4) |
|---|---|---|
| `0x01` | 0 | out of case, lid open, not in ear |
| `0x50` | 4, 6 | transitioning: pod in case, lid open |
| `0x54` | 2, 4, 6 | both in case, lid open |
| `0x55` | 0, 2, 4, 6 | both in case, lid **closed** |

### Unknown-value encodings (observed live, not from documentation)

| Nibble value | Meaning | Seen as |
|---|---|---|
| `0xF` | battery unknown | right bud during a lid-open transition |
| `> 10` (e.g. `0xB`) | case battery unknown | case while the lid was closed |

A parser that clamps rather than checks for `0xF` would render "150 %". This is the single
most likely user-visible bug class and now has a real fixture.

## 2. Addresses rotate — identity is a real problem

One pair, four addresses inside 150 s:

| Address | Packets | First | Last | RSSI |
|---|---|---|---|---|
| `0x6BE0048EE8FD` | 24 | 0 s | 94.7 s | −127 … −40 dBm |
| `0x66F821F6B909` | 18 | 38.8 s | 61.5 s | −52 … −41 dBm |
| `0x5CEB8743B678` | 25 | 72.5 s | 94.7 s | −56 … −45 dBm |
| `0x6D6BCA3BE7E3` | 1 | 119.2 s | 119.2 s | −58 dBm |

Same product ID, same battery levels, overlapping windows. This is resolvable-private-address
rotation, and it means **an address is not an identity**: a UI keyed on `BluetoothAddress`
would show one pair as a new device every ~30 s. The −127 dBm row is out-of-range noise on
the address that spans the whole window and should be filtered by RSSI.

**Design consequence (feeds APW-018):** group adverts by product ID + battery signature +
continuity over time, keep a single logical "my AirPods" record, and treat addresses as
ephemeral. Multi-pair disambiguation remains unsolved without the IRK.

## 3. Cadence and latency

| Metric | Value |
|---|---|
| Inter-packet interval, median | **977 ms** |
| p95 | 4 126 ms |
| Max | 24 517 ms |
| Min | 55 ms |

The 20–30 s figure in the research documents is wrong for an active, in-range device: it
advertises about **once a second** while out of the case, and goes silent within a second or
two of the lid closing.

Closed → open detection gaps, measured as time since the previous packet:

| Trial | Gap |
|---|---|
| 1 | 4 126 ms |
| 2 | 284 ms |
| 3 | 24 517 ms |

These are **upper bounds**, not true latencies: we only see the first packet carrying
`lid = open`, so the real delay is ≤ the gap. Trial 3 includes the whole closed-lid silence.

**Conclusion for the popup target (APW-109, ≤ 1.5 s p95):** achievable in the common case
(median cadence ≈ 1 s) but **not guaranteed** after a long closed period, where the first
advert can take seconds. The trigger must therefore also react to a *burst* of adverts after
silence, and the UI must tolerate a late popup rather than assume instant delivery.

---

## 4. What this means for the design

1. **Deduplicate by content, not address.** Otherwise RPA rotation multiplies devices.
2. **Model `unknown` explicitly.** `0xF` and case `> 10` are normal states, not errors.
3. **Handle silence.** A closed lid is indistinguishable from "walked away" without a
   timeout; staleness (> 5 s) must clear the popup rather than freeze it.
4. **Do not trust a single packet** for lid state; require the status bits and the lid bit to
   agree (e.g. `0x50`/`0x54` are transitional).
5. **RSSI needs a floor** (~ −85 dBm) to drop phantom reports like the −127 dBm row.
