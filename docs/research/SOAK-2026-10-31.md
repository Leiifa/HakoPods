# APW-103 soak — 2026-10-31

Ten minutes of live traffic, two independent readers on the same adapter at the same time.

| Reader | What it counts | Result |
|---|---|---|
| `BleProbe --capture 600` (reference) | every Apple `0x004C` / `0x07` packet from the OS | **499** |
| `Soak` (new `ProximityPairingService`) | raw packets at the watcher, plus emitted samples | **499 raw → 493 emitted** |

**Loss: zero.** The two readers agree exactly, packet for packet, over 600 s.

## Details

| Metric | Value |
|---|---|
| Duration | 600 s |
| Raw pairing packets | 499 (≈ 0.83 / s) |
| Emitted after parse + dedupe | 493 (99 %) |
| Suppressed as duplicates | 6 (1.2 %) |
| Other Apple traffic (non-`0x07`) | 131 — correctly ignored |
| Distinct addresses | 4 (rotating, as expected) |
| RSSI range | −127 … −45 dBm (phantoms present) |
| Watcher restarts | 0 |
| Working set | 51 → 52 MB, flat |

## What this proves

- The watcher adapter and the service's filter lose nothing that the raw reader sees.
- The 250 ms dedupe window is **not** eating real updates: at ~1 packet/second it only
  suppresses exact repeats delivered twice by Windows.
- Non-proximity Apple traffic (131 packets) is correctly discarded rather than mis-parsed.
- No memory drift over ten minutes.

## What it does **not** prove

- **Auto-restart after sleep or a radio toggle.** Nothing stopped the watcher during the run,
  so `RestartCount` stayed 0. That path is covered by unit tests only; a real suspend/resume
  test is still worth doing once, by hand.
- **Multi-pair behaviour** — one pair was present.
- **Application memory.** The 52 MB is the console harness, not the WPF app; APW-310 measures
  the real budget.

## Reproduce

```
./spike/ble-probe/bin/Release/net8.0-windows10.0.19041.0/BleProbe.exe --capture 600 --out docs/captures/soak.md
./spike/soak/bin/Release/net8.0-windows10.0.19041.0/Soak.exe --minutes 10
```

Both must run at the same time; the comparison is between their raw counts.
